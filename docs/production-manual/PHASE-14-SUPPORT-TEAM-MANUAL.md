# Phase 14: Support Team Manual — Production Operations Manual

> **Purpose:** Provide customer support with a complete decision tree and action guide for every possible order/invoice/shipment state. This is NOT a developer document — it is the support team's runbook.

---

## 14.1 Order Status Decision Tree

### Order Status: `pending`

| Question | Answer |
|----------|--------|
| What happened? | Customer submitted order, payment not yet received (online: waiting for gateway callback; COD/cashier: waiting for payment confirmation) |
| What customer sees? | "Order placed — awaiting payment" with order number |
| What admin sees? | Order in list with status `pending`, transaction status `pending` |
| Can support fix it? | Limited |

Actions:
```
Is the payment method online?
  ├── YES → Check Transaction.gateway_transaction_id
  │   ├── Has gateway_transaction_id?
  │   │   ├── YES → Check gateway for payment status via PaymentReconciliationJob
  │   │   │   ├── Gateway says PAID → Trigger callback manually? NO — must fix via DB or rebuild
  │   │   │   └── Gateway says PENDING/FAILED → Wait or ask customer to retry
  │   │   └── NO → Customer may not have completed payment. Ask them to retry.
  │   └── No transaction? → Order created without transaction. Rare bug. Escalate.
  │
  ├── COD → Mark as paid via admin (permission: update-order-status). 
  │         If customer wants to cancel → cancel order.
  │
  └── Pay at cashier → Customer has QR code. If they paid in store:
        Mark as paid via admin (permission: update-order-status).
```

**Can support:**
- ✅ Cancel order (if customer requests)
- ✅ Mark COD/cashier as paid
- ❌ Retry online payment (customer must do this from frontend)
- ❌ Modify order items/prices
- ❌ Regenerate invoice (no invoice yet)

### Order Status: `processing`

| Question | Answer |
|----------|--------|
| What happened? | Payment received, order is being prepared for fulfillment |
| What customer sees? | "Order is being processed" |
| What admin sees? | Order in list with status `processing` |
| Invoice? | Should exist (generated by GenerateInvoiceListener) |

Actions:
- Normal flow. No support action needed unless customer wants to cancel.
- **Cancel allowed?** Yes — `processing → cancelled` is allowed.
- **Cancel effect:** Promotion usage decremented; inventory restored (via RestoreProductInventory listener, guarded by `inventory_restored_at`); coupon NOT reversed.

### Order Status: `completed`

| Question | Answer |
|----------|--------|
| What happened? | Payment received, order finalized (or marked as paid for COD/cashier) |
| What customer sees? | "Order completed" |
| What admin sees? | Order in list with status `completed` |
| Invoice? | Must exist. If missing → check GenerateInvoiceListener queue |

Actions:
- **Cancel allowed?** No — `completed` cannot go to `cancelled`
- **Refund allowed?** Yes — create refund request, admin approves
- **Invoice issues?** Support can regenerate PDF or correct invoice

### Order Status: `delivered`

| Question | Answer |
|----------|--------|
| What happened? | Customer received the order |
| What customer sees? | "Delivered" |
| What admin sees? | Status `delivered` (terminal) |
| Invoice? | Should be in `verified`, `downloaded`, or `printed` status |

Actions:
- Terminal state. No status changes allowed.
- Refund via separate refund process.
- Return via separate return process (NOTE: return system not built yet).

### Order Status: `cancelled`

| Question | Answer |
|----------|--------|
| What happened? | Order was cancelled (by customer, admin, or system) |
| What customer sees? | "Cancelled" |
| What admin sees? | Status `cancelled`, `cancelled_at` timestamp set |
| Invoice? | If invoice was generated, it stays in its current status (NOT auto-cancelled) |

Actions:
- Terminal state. No further status changes.
- Inventory was restored (via RestoreProductInventory listener).
- Coupon quota was consumed (NOT reversed).
- Promotion usage was decremented.
- Invoice NOT auto-cancelled — must be manually cancelled if needed.

## 14.2 Payment Status Decision Tree

### Payment: `payment-pending`

**What happened?** Payment not yet received or transaction not yet confirmed.

**Customer sees:** "Awaiting payment"
**Can support retry?** Only for online payments — customer must retry from frontend.
**Can support mark as paid?** Only for COD and cashier payments.

### Payment: `payment-success`

**What happened?** Payment confirmed.

**Customer sees:** "Payment successful"
**Can support refund?** Yes — process refund via admin panel.

### Payment: `payment-failed`

**What happened?** Payment failed at gateway or amount/currency mismatch detected.

**Customer sees:** "Payment failed" with error message
**Can support retry?** Customer must retry from frontend with new checkout.
**Can support fix?** If gateway actually has the payment but our system marked as failed (BUG-4 scenario), this is a reconciliation issue. Escalate to engineering.

### Payment: `payment-refunded`

**What happened?** Payment was refunded to customer.

**Customer sees:** "Refunded" (if displayed)
**Can support reverse?** No.

## 14.3 Invoice Status Decision Tree

### Invoice: `generated`

**What happened?** Invoice record created in DB, PDF job dispatched.
**Can support regenerate?** Yes — via admin `POST /invoices/{id}/regenerate`
**Can support correct?** Yes — via admin `POST /invoices/{id}/correct`
**Can support cancel?** Yes — via admin `POST /invoices/{id}/cancel`
**PDF?** May or may not exist yet (PDF job runs on `low` queue).

### Invoice: `pdf_generating`

**What happened?** PDF generation is in progress (or stuck).
**Can support retry?** Yes — regenerate endpoint sets status to `pdf_generating` again.
**If stuck?** Check queue worker. If queue is down, restart worker and re-dispatch.

### Invoice: `ready`

**What happened?** PDF generated successfully (or placeholder marked as ready).
**Can support download?** Yes — if `pdf_path` exists.
**Can support correct/cancel?** Yes.

### Invoice: `failed`

**What happened?** PDF generation failed.
**Can support retry?** Yes — regenerate endpoint.
**Check:** `last_generation_error` field for failure reason.

### Invoice: `verified`

**What happened?** Someone verified this invoice via the public verification endpoint.
**Can support correct/cancel?** Yes.

### Invoice: `downloaded`

**What happened?** Customer or admin downloaded the PDF.
**Can support correct/cancel?** Yes.

### Invoice: `corrected`

**What happened?** Invoice was corrected — new correction invoice exists.
**Original invoice:** Status set to `corrected`. Correction invoice has `correction_to_id` pointing to original.
**Can support cancel?** Yes — `corrected → cancelled` is allowed.
**Can support re-correct?** Correct the correction invoice (new ID).

### Invoice: `cancelled`

**What happened?** Invoice was cancelled.
**Can support uncancel?** No — terminal state (only `archived` allowed).
**Can support regenerate?** No — must issue new invoice via order.

### Invoice: `archived`

**What happened?** Invoice archived for long-term storage.
**Can support anything?** No — fully terminal.

## 14.4 Shipment Status Decision Tree

### Shipment: `pending` → `label_created` → `picked_up` → `in_transit` → `out_for_delivery` → `delivered`

Happy path. No support action needed.

### Shipment: `failed_delivery`

**What happened?** Courier could not deliver.
**Actions:**
- Support can retry delivery by transitioning to `out_for_delivery` again (allowed transition).
- Customer can arrange pickup.
- If repeatedly failing, escalate to courier management.

### Shipment: `returned`

**What happened?** Shipment returned to sender.
**Actions:**
- Terminal state.
- Initiate refund or resend.

### Shipment: `delayed`

**What happened?** Shipment is behind schedule.
**Actions:**
- Can transition to `in_transit` or `out_for_delivery`.
- Inform customer of delay.

### Shipment: `cancelled`

**What happened?** Shipment cancelled (before pickup).
**Actions:**
- Terminal state.
- Arrange alternative shipping.

## 14.5 Common Support Scenarios

### Scenario 1: "I paid but my order is still pending"

```
1. Check if payment gateway callback was received
2. Look for Transaction with status 'pending' and gateway_transaction_id
3. Run PaymentReconciliationJob or manually verify with gateway
4. If gateway confirms payment:
   → Engineering must manually update transaction to 'paid' and order to 'completed'
   → This triggers invoice generation
5. If gateway has no record:
   → Ask customer to check bank statement
   → If charged, initiate chargeback via gateway
```

### Scenario 2: "I didn't receive my invoice"

```
1. Check if Invoice exists for the order
2. If no invoice → check GenerateInvoiceListener queue
   - Queue worker running? Check horizon/telescope
   - If failed, manually trigger: PHP artisan tinker → dispatch GenerateInvoiceListener
3. If invoice exists but no PDF → regenerate PDF via admin
4. If PDF path exists → provide download URL to customer
```

### Scenario 3: "My coupon didn't work"

```
1. Check if coupon code exists and is valid (status=true, not expired, limiter not reached)
2. Check if it was applied to the cart at checkout time
3. If coupon was valid but auto-cleared:
   → Cart.refresh() issue (CPN-1) — coupon was valid at apply time but expired by checkout
   → No recovery — coupon quota cannot be retroactively consumed
   → Offer customer a new coupon as compensation
```

### Scenario 4: "I want to cancel my order"

```
1. Check order status:
   ┌ pending → CAN cancel
   ├ processing → CAN cancel
   ├ completed → CANNOT cancel (must refund)
   ├ delivered → CANNOT cancel (must refund)
   └ cancelled → Already cancelled
2. If cancelling:
   → Promotion usage decremented
   → Inventory restored (may be queued)
   → Coupon NOT reversed
   → Invoice NOT auto-cancelled (cancel manually if needed)
```

### Scenario 5: "I want a refund"

```
1. Check order status: must be completed or delivered
2. Check payment status: must be payment-success
3. Process refund via admin panel:
   → RefundApproved event fires
   → Inventory restored (queued)
   → Credit note generated (queued)
   → Invoice marked as corrected
4. Payment gateway refund:
   → MyFatoorah refund gateway handles this
   → Not yet integrated in app code
```

## 14.6 Error Message Reference

| Error Key | Displayed Message (EN) | Meaning | Support Action |
|-----------|----------------------|---------|----------------|
| CART_NOT_FOUND | Cart not found | Customer tried to checkout with no active cart | Ask customer to add items first |
| QUANTITY_EXCEEDS_STOCK | Quantity exceeds available stock | Not enough inventory | Offer alternative quantity or product |
| COD_NOT_AVAILABLE_FOR_PICKUP | COD not available for pickup | Cannot use COD with pickup fulfillment | Switch to delivery or different payment |
| INVALID_PAYMENT_METHOD | Invalid payment method | Unsupported payment method | Escalate |
| ERROR_CREATING_INVOICE | Failed to create payment invoice | Gateway rejected the payment request | Check gateway configuration |
| MISSING_PAYMENT_ID | Missing payment ID | Callback received without paymentId | Check gateway callback configuration |
| CHECKOUT_SUCCESSFUL | Checkout successful | Order + transaction created | No action needed |
| PAYMENT_SUCCESSFUL | Payment successful | Payment confirmed | No action needed |
| PAYMENT_FAILED | Payment failed | Gateway reported failure or mismatch | Check gateway logs, ask customer to retry |
| NOT_FOUND | Resource not found | Requested entity doesn't exist | Verify ID/UUID |

## 14.7 Escalation Matrix

| Issue | First Line | Second Line | Third Line |
|-------|-----------|-------------|------------|
| Payment mismatch | Support checks gateway | Admin runs reconciliation | Engineering fixes data |
| Invoice missing | Support checks queue | Admin regenerates | Engineering debugs |
| Bug in checkout | Support documents | QA reproduces | Engineering fixes |
| Gateway down | Support informs customer | Admin contacts gateway | Engineering switches fallback |
| Data corruption | Support isolates | Admin backups | Engineering restores |
