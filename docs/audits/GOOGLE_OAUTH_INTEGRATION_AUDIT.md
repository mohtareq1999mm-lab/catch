## 1. Executive Summary

Google login currently fails at the **Google consent screen** with `Error 400: redirect_uri_mismatch`.

The backend's OAuth implementation itself is functional and correctly wired: it generates a Google authorization URL (verified live in production), handles the callback, creates/links users, issues single-use codes, and redirects the browser to the frontend with the code (verified live). The frontend (deployed at `https://catch-beauty-ecommerce-v0-kappa.vercel.app`, which is a **Next.js** app, *not* Angular as believed) correctly calls the backend through a same-origin Vercel proxy and implements the code-exchange contract (verified from its deployed JS bundles).

The failure mechanism:

1. The backend builds `redirect_uri` from the **incoming request's host** (`url()` helper — `SocialController::callbackUrl()`, L209–212).
2. The frontend app calls the backend through **its own Vercel domain** (relative base `/api/v1` + rewrite proxy). Live test proved that in this path the generated `redirect_uri` is `https://catch-beauty-ecommerce-v0-kappa.vercel.app/api/v1/social/google/callback`.
3. Google rejects any `redirect_uri` that is not exactly registered in the Google Cloud Console for OAuth client `494344424703-39rali7ac6ntdnueivo3m11p93j3hf20.apps.googleusercontent.com`. The observed `redirect_uri_mismatch` proves the console's registered URIs do **not** include the URI actually used by the real frontend flow.

**Primary root cause:** Google Cloud Console configuration (external) — the Authorized redirect URIs registered for the client do not match the redirect URI generated by the live frontend flow. **Contributing design weakness (backend):** the `redirect_uri` is nondeterministic (it varies by which URL initiates the call), which makes the console registration fragile; an env var intended to control it (`GOOGLE_REDIRECT_URI`) exists in `.env`/`.env.example` but is **dead code** — it is never used by the current flow.

No code change is required to unblock login; registering the correct redirect URI(s) in Google Cloud Console is the minimum safe fix.

## 5. Expected Authentication Flow (for this architecture)

Same as §4, but with a **deterministic, allow-listed `redirect_uri`**:

```
Frontend (Next.js, vercel)
  └─ GET  /api/v1/social/google            (same-origin → Vercel rewrite → backend)
        └─ Backend returns {success, url}  with redirect_uri = EXACTLY a URI registered in Google Console
  └─ Browser → Google (accounts.google.com/o/oauth2/auth?...&redirect_uri=<registered>&state=web)
        └─ Google consent → redirects to the registered callback (frontend-domain callback is valid here
           because the Vercel proxy forwards it to the same backend controller)
              └─ Backend callback: exchange code ↔ Google (redirect_uri must equal the one used in step 2 —
                 it does, because the callback request arrives through the same proxy and resolves the same host)
                    └─ create/link user → one-time code → 302 to frontend  /?code=<code>
  └─ Frontend reads ?code → server action → POST /api/v1/social/exchange {code}
        └─ Backend: atomic claim → Sanctum token → {token, user}
  └─ Frontend sets session; subsequent calls use Bearer token
```

**Critical property of the current implementation:** whichever domain is used to *initiate* (frontend domain via proxy, or backend domain directly) consistently appears in both the authorization request and the token exchange — live tests A1/A5 + proxy behavior prove both paths are internally consistent. Therefore **both** callback URIs are valid candidates for the Google Console allow-list; at minimum, the URI generated by the *real frontend flow* (frontend domain) must be registered.

## 9. API Contract

### 9.1 `GET /api/v1/social/{provider}` (alias `GET /api/v1/social/redirect?provider=...`)

- **Auth:** none (public; `throttle:login`, `lang`).
- **Query:** optional `type=web|mobile` (default `web`); unknown values → `web`.
- **Response 200:** `{ "success": true, "url": "<Google authorization URL>" }`
  - `url` contains: `client_id`, `redirect_uri` (= request-host-derived callback), `scope=openid+profile+email`, `response_type=code`, `state=<web|mobile>`.
- **Errors:** 500 envelope `{message:"Please login using Facebook or Google"}` on invalid provider (MarvelException; observed historically in e2e evidence).
- **Owner:** Backend. **Consumer:** Frontend (then redirects the browser itself).

### 9.2 `GET /api/v1/social/{provider}/callback`

- **Auth:** none (public). Called by **Google's browser redirect**, not by the frontend.
- **Query (from Google):** `code`, `state` (echoed client type), optional `error`.
- **Success (web):** `302 → {frontend_url}/?code=<one-time-code>` (code TTL from config; default 200 min).
- **Success (state=mobile):** `200 { "success": true, "code": "<one-time-code>" }`.
- **Failure (web):** `302 → {frontend_url}/auth?error=social_login_failed` — **VERIFIED live** (probe A2).
- **Failure (state=mobile):** `400 { "success": false, "message": "Social login failed, please try again." }` (localized en/ar).
- **Side effects:** creates/links user, creates `social_login_codes` row.

### 9.3 `POST /api/v1/social/exchange`

- **Auth:** none (public). Called by the **frontend** (browser or Next.js server action) with the one-time code.
- **Body:** `{ "code": "<64-char hex>" }` (validated: required, string, max 64).
- **Response 200:** `{ "success": true, "message": "Login successful.", "token": "<Sanctum PAT>", "token_type": "Bearer", "user": { ...UserResource with roles } }`
- **Errors:** 400 `{success:false, message:"Invalid or expired authorization code."}` (unknown/expired/replayed/inactive user); 422 on missing/invalid `code`.
- **Guarantees (TESTED by suite; code-verified):** single-use (atomic claim), delete-on-use, replay → 400, expiry → 400.

### 9.4 `POST /api/v1/social-login-token` — **NOT REGISTERED** (F-07)

`UserController::socialLogin` (`{provider, access_token}` → Sanctum token, 1-week expiry) exists in code and is documented via OpenAPI annotations (`/social-login-token`), but **no REST route exists** (`route:list` verified). Reachable only through the GraphQL mutator (`AuthMutator::socialLogin` L54–56). The related REST tests (`UserAuthAdminTest` L320–342) are pre-existing failures by inspection (they expect 500/422; the route returns 404).

### 10.4 Why the error happens at Google's step 5

Google's `redirect_uri_mismatch` is raised **before consent**, when the `redirect_uri` parameter of the authorization request is not exactly present in the client's Authorized redirect URIs. The real frontend flow presents URI **B** (probe A5). The user's error therefore proves **B is not registered** (or is registered with any byte-level difference). Whether **A** is registered cannot be determined from here.

Historical corroboration: `storage/e2e/authgroup/evidence-20261018-113443.jsonl` (entry `E4-A1-ALIAS-GOOGLE`) shows the same generation mechanism locally: `redirect_uri=http://127.0.0.1:8000/api/v1/social/google/callback` (request-host-derived; at that time `client_id` was empty in that environment) — the mechanism, not the console, generates the value.

## 15. Final Verdict

1. **Is the Backend implementation correct?** Yes for the implemented contract: initiation URL generation (live-verified), callback handling, user create/link, single-use code exchange, error redirects (live-verified error path). It is *correct but fragile* — the `redirect_uri` is request-host-derived (F-01/RC-2), and there are hygiene issues (dead `GOOGLE_REDIRECT_URI`, missing `login` rate limiter, unregistered `social-login-token` endpoint).
2. **Is the Frontend implementation correct?** Yes — as deployed, the Next.js app's OAuth flow matches the backend contract exactly (initiation, `?code=` handling, exchange, error mapping). Repository-level verification was impossible (repo not available); the server-side exchange action is INFERRED from naming + contract. The "Angular" premise was contradicted by evidence.
3. **Is the Google OAuth configuration correct?** **No** — the observed `redirect_uri_mismatch` proves the client's registered redirect URIs do not include the URI used by the real flow. Exact console contents UNKNOWN.
4. **Is the integration contract consistent?** Yes — Backend and Frontend contracts align end-to-end (verified from code + bundles + live probes). The single broken link is external (Google Console).
5. **What exactly causes the redirect_uri_mismatch?** The authorization request carries `redirect_uri=https://catch-beauty-ecommerce-v0-kappa.vercel.app/api/v1/social/google/callback` (the request-host-derived callback, because the frontend initiates through its own Vercel proxy — probe A5), and this URI is not registered in the Google Cloud Console for client `494344424703-…`. Google rejects pre-consent with Error 400.
6. **Can the current implementation complete Google Login?** Not until the Google Console registers the correct redirect URI(s). After that, all remaining steps are implemented and (per the test suite contract) expected to work; the success path has not been executed end-to-end in this audit (would require real Google credentials — out of scope).
7. **What is the minimum safe fix?** Register in Google Cloud Console: `https://catch-beauty-ecommerce-v0-kappa.vercel.app/api/v1/social/google/callback` **and** `https://catch.mohammedtareq.me/api/v1/social/google/callback` (exact strings, no trailing slash). No code change required.
8. **What should be tested after the fix?**
   - Manual E2E: click Google login on the deployed frontend → consent → callback → land on `/?code=…` → session established → call `GET /api/v1/me` (or equivalent authenticated endpoint) with the Bearer token.
